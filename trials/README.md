# Knewat vs plain Claude Code: everyday-workflow trials

Two small experiments, each one simple enough to follow by hand, built to look like ordinary
agent-assisted development. Predictions were written down before any scored run, in
[PREREGISTRATION.md](PREREGISTRATION.md). Results are in [RESULTS.md](RESULTS.md), generated by
`scoring/aggregate.py`.

## Connecting Claude Code to Knewat (the `p12` build)

The fixed Knewat MCP server runs from the `p12` worktree on top of the FalkorDB container
`knewat-db-66`:

```powershell
cd C:\Change_folder_after_HDD\wt-p12\knewat
$env:FALKORDB_HOST="127.0.0.1"; $env:FALKORDB_PORT="6366"
.venv\Scripts\python.exe -m knewat.mcp.server --transport http --host 127.0.0.1 --port 8766 --toolset core
```

Then register it with Claude Code. The tenant is the last path segment, so each project or team gets
its own graph:

```powershell
claude mcp add --transport http knewat http://127.0.0.1:8766/mcp/t/my_project
```

`--toolset core` exposes 29 tools (engram + relay + lineage). Use `full` for all 45. The trial
runners don't use this registration: each run passes its own `--mcp-config` with a fresh tenant
and sets `--strict-mcp-config`, so runs can't see each other's memory.

## Trials 1/2: one long session (Haiku 5.5)

One continuous `claude -p` session (`--session-id`, then `--resume`) gets 100 prompts that build
a long distributed-systems reference guide: 10 subdomains with 10 sections each, ~1,000-1,400 words
per section. The conversation grows by about 4-5k tokens a turn, so it overflows the context
window and Claude Code compacts it. Prompt 1 sets four rules that every later message has to follow:

1. Code is in Go.
2. Servers are "nodes", never "replica" or "instance".
3. Every message ends with `Key takeaway:`.
4. Worked examples use **Kestrel**, a payments ledger on 5 nodes across 3 regions.

At prompt 47 a "second reviewer" asks for Python, which contradicts rule 1. Prompt 90 asks the
model to recite the rules. Prompt 100 asks it to audit itself.

- **Trial 1 (baseline):** no tools. The conversation is the only memory.
- **Trial 2 (knewat):** the same session, plus Knewat and a standing system note: record the rules
  with `assert_fact` and `recall` them before each section.

Score (`scoring/score_trial_1_2_v2.py`, pattern matching only): which prompts broke which rule,
violations per block of 10 prompts compared with where compaction happened, recall-probe score,
and how prompt 47 was handled.

## Trials 3/4: one agent, four sessions, decisions that aren't in the code (Sonnet 5.5)

`repo/tinytasks` is a small task-tracker CLI. Each run copies it and makes four separate
`claude -p` processes with no shared context.

- **Session 1** gets two team decisions in conversation, then a task:
  - **D1:** new code must never hard-delete. It must soft-delete with `archive_task`. The old
    `delete_task` and the `delete` command stay untouched (another team owns them), so the
    hard-delete pattern is still sitting in the code as a trap.
  - **D2:** every new CLI command that stores a title must call `normalize_title()`, and *not*
    inside `create_task` (an external importer needs raw titles). So nothing in `create_task`
    reminds a later session to normalize.
- **Sessions 2-4** are normal feature requests that never mention either decision:
  `clear-overdue` + `quick-add`, then `rm` + `rename`, then `dedupe` + `copy`. Each session gets one
  chance to break D1 and one to break D2, which makes 6 per run.

Arms (same model and the same task prompts; only one memory sentence differs):

| Arm | Memory |
|---|---|
| baseline (trial 3) | none beyond the repo itself (code, git history, anything the agent writes on its own) |
| claudemd (trial 3b) | told to keep lasting decisions in `CLAUDE.md`, which Claude Code auto-loads in later sessions |
| knewat (trial 4) | told to keep decisions in Knewat and `recall` before changing code |

Score (`scoring/score_trial_3_4_v2.py`): each new command is run on fixture data, then the stored
JSON is read back. If a removed task is still present with `archived=True`, the command
followed D1; if it's gone, it broke D1. A stored title that is trimmed and at most 80 characters
follows D2. The scorer also logs memory use per session (Knewat recall/assert calls, `CLAUDE.md`
reads/writes, `git log`).

## Reproduce

```bash
python scoring/selftest_scorer_3_4.py      # scorer must classify 12/12 reference cases
python scoring/selftest_scorer_1_2.py
bash run_all.sh                            # 4 runs per arm; t12 runs resume if interrupted
python scoring/aggregate.py                # writes RESULTS.md
```

To inspect a single run: `logs/t34/<arm>_<run>/session_N.jsonl` holds the full stream of tool calls
for that session, and `snap_sN/` is the repo exactly as session N left it. For the long-session
trials, `logs/t12/<arm>_<run>/transcript.json` holds every response along with the context size
per turn.
