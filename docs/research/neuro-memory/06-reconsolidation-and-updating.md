# 06. Reconsolidation and memory updating: prediction-error-gated reliability

Research note for Plexus. `[unverified]` = not confirmed against an opened source.

## 1. Mechanism

### 1.1 Retrieval makes a consolidated memory labile again

Nader, Schafe & LeDoux (2000): "consolidated fear memories, when reactivated during retrieval, return to a labile
state in which infusion of anisomycin shortly after memory reactivation produces amnesia on later tests, regardless
of whether reactivation was performed 1 or 14 days after conditioning"; without reactivation the same drug left
memory intact, and delaying the infusion by six hours produced no amnesia [1]. So there is a post-retrieval window
(hours) in which the memory is rewritten, and it closes.

### 1.2 The boundary condition: prediction error is required

Sevenster, Beckers & Kindt (2013, 2014): "prediction error (PE), a mismatch between what is expected based on
previous experiences and the actual state of events, is a necessary condition for inducing reconsolidation of human
associative fear memory upon retrieval"; post-retrieval changes in expectancy "demarcate the transition from
retrieval, to reconsolidation, to new learning": no PE → retrieval only; moderate PE → the old trace is updated;
large/sustained PE → a *new* trace is formed and the old one stays [2]. Exton-McGuinness, Lee & Reichelt (2015)
review the same conclusion across species [3]. Sinclair & Barense (2019) generalise it: "incomplete reminders …
retrieval cues that partially replicate an encoding experience allow memories to be distorted, updated, and
strengthened", and frame it under predictive coding [4].

### 1.3 The computational form: latent-cause inference

Gershman, Monfils, Norman & Niv (2017): memory modification "occurs through classical associative learning, but
which memory trace is eligible for modification depends on a structure learning mechanism that … segment[s] the
stream of experience into statistically distinct clusters (latent causes). New memories are formed when the
structure learning mechanism infers that a new latent cause underlies current sensory observations. By the same
token, old memories are modified when old and new sensory observations are inferred to have been generated by the
same latent cause" [5]. The model reproduces the reconsolidation findings, including that a short retrieval before
extinction updates the fear memory while a long one creates a new trace.

This is, word for word, the decision `assert_fact` makes: *same cause* → supersede (update), *new cause* →
a new fact that `CONTRADICTS` (both stay), *no new information* → duplicate.

## 2. Why it matters for recall QUALITY

Plexus's `confidence` is a float set at assert time and never touched again. Nothing that happens *after* a fact is
used feeds back into it: a decision built on it gets flagged, a task that relied on it fails, a `verify_fact`
finds it changed, another agent contradicts it. The graph records all of those as edges, but recall ranks by
relevance and activation only. The retrieval error this causes: **a fact that has been contradicted by outcomes
keeps its rank until someone supersedes it by hand.** MemoryAgentBench's selective-forgetting task (forgetting-A
§2.7) is exactly this, and every system scored ≤ 28% on the multi-hop version.

Reconsolidation gives the rule for a disciplined feedback: update only on a prediction error (an outcome that
mismatches), with magnitude scaled by the surprise, and only for the trace that was *retrieved into* that step.

## 3. Design for Plexus

### 3.1 Schema: a Beta posterior per fact

`Fact.rel_a: float` (default 2.0) and `Fact.rel_b: float` (default 1.0); `reliability = rel_a / (rel_a + rel_b)`
(prior 0.67). `confidence` (the asserting agent's own claim) stays untouched; `reliability` is Plexus's evidence
from outcomes. `memory_strength` prints both, with the events that moved `rel_a`/`rel_b`.

### 3.2 The reconsolidation rule (prediction-error gate)

An *outcome* is any write that closes the loop on a step that `READ via:'use'` the fact:

| outcome write | PE? | update to the facts used by that step |
|---|---|---|
| `record_decision` (unflagged) | none | nothing (retrieval without PE: no reconsolidation) |
| `verify_fact(confirmed)` | none | `rel_a += 0.5` (mild strengthening; a passed test) |
| `verify_artifact(independent=true, passed)` on an artifact of a task decided on the fact | none | `rel_a += 0.5` |
| `fail_task` on a task whose decision is `BASED_ON` the fact | PE | `rel_b += 1.0` |
| decision flagged (quarantine, forget, backdate) | PE | `rel_b += 1.0` |
| `verify_fact(changed)` | PE, large | old fact: superseded (status); `rel_b += 2.0` on it so `as_of`-style views of history show it as unreliable at its end |
| `assert_fact` from a different agent that `CONTRADICTS` | PE, moderate | both sides: nothing yet (two claims, no outcome); the next outcome on either side decides |

Within-window rule (Nader): only steps whose `READ` happened within 24 h before the outcome write are updated
(the window is generous because agent steps are minutes to days apart; the point is that an outcome does not
reach back to every use ever).

### 3.3 Exact Cypher: in the same statement as the outcome

Example for `fail_task`, appended to the existing task write (one statement, bounded):

```
MATCH (t:Task {id:$task_id, status:'claimed'})
SET t.status = 'failed', t.failed_at = $now, t.failure = $reason
WITH t
OPTIONAL MATCH (d:Decision)-[:DECIDED]->(t)            // decisions about this task (≤ 20)
WITH t, collect(d)[0..20] AS ds
UNWIND (CASE WHEN size(ds) = 0 THEN [null] ELSE ds END) AS d
OPTIONAL MATCH (d)-[:BASED_ON]->(f:Fact)
WHERE f IS NOT NULL AND d.created_at >= $now - 86400000
WITH t, collect(DISTINCT f)[0..50] AS fs
FOREACH (f IN fs | SET f.rel_b = coalesce(f.rel_b, 1.0) + 1.0, f.rel_at = $now)
RETURN t.id, size(fs) AS facts_updated
```
(6.0.2: `FOREACH … SET` is the bounded write form that works after an aggregation; the `[0..50]` slice bounds it.
If the planner refuses `FOREACH` after `UNWIND`+`OPTIONAL MATCH`, split into the second statement of the tool with
the ids carried in Python, as `verify_fact` does for its backdate.)

For `verify_fact(confirmed)`: `SET f.rel_a = coalesce(f.rel_a, 2.0) + 0.5` inside the statement that creates
`VERIFIED_BY`. For a flagged decision (`forget_source`, `quarantine_source`, `backdate`): the statements already
`SET d.flagged = true`; add the `BASED_ON` walk and the `rel_b` increment in the same statement, bounded by the
existing per-level caps.

### 3.4 Latent-cause inference for `assert_fact`

Today's rule (`assert_fact.cypher`): same normalised value → duplicate; same agent or `supersede=true` → supersede;
different agent, different value → `CONTRADICTS`. Gershman's model adds *time* and *similarity* to the decision.
A deterministic version with explicit thresholds:

```
given current fact c for (entity, predicate, scope) and new value v from agent g:
  sim        = cosine(embed(v), c.embedding)
  since_use  = now − last READ{via:'use'} of c (∞ if never)
  if dedup says duplicate                                  → duplicate (today's rule, unchanged)
  elif g ∈ asserters(c) or supersede=true                  → supersede (same cause, author updates)
  elif c.reliability < 0.5                                 → supersede, with CONTRADICTS kept as history
                                                            (the old trace was already discredited by outcomes: update it)
  elif since_use > 30 d and sim > 0.6                      → supersede (an old, unused claim replaced by a near variant:
                                                            same cause, drifted)
  else                                                     → CONTRADICTS, both active (new cause: two live claims)
```
Only the two middle branches are new, and both are conservative: they move a case from "two live contradicting
facts forever" to "updated, with the contradiction recorded". The thresholds (0.5, 30 d, 0.6) are stated so the
benchmark can falsify them. `surprise` for the new fact stays as today (0.6 supersede / 0.9 contradict).

### 3.5 Reliability in the recall score

Add to the additive score (note 01): `+ ρ · ln(reliability / 0.67)` with `ρ = 1.0`: at the prior it is 0; a fact at
reliability 0.4 (one failed outcome, no confirmations: `2/(2+2)`) loses `ln(0.6) = −0.51` nats, which is a 40%
relative relevance penalty — enough to drop below a correct twin, which is the point; three confirmations
(`3.5/4.5 = 0.78`) gain `+0.15`. Reliability is **not** the same axis as salience (note 05) or surprise: a fact can be
important and unreliable (a flagged decision rests on it) and the three numbers say so separately.

### 3.6 `why_confidence(fact)`

Read-only: returns `confidence` (asserted), `reliability` with `rel_a`, `rel_b`, and the list of outcome events
that moved them, each with the path (`fact ← BASED_ON ← decision → DECIDED → task (failed at …)` or
`fact → VERIFIED_BY {outcome} → agent`). It is `why` run backwards from outcomes, over edges that already exist
plus `rel_at`.

## 4. Benchmark plan

**L5b-correction variant.** Take L5b, and for 20% of the real facts inject a *wrong twin* (same entity and
predicate, a plausible different value, asserted by a second agent → `CONTRADICTS`), then in the read schedule let
a decision be recorded on the wrong twin and the task it decides *fail* at day 30, while the right fact gets one
`verify_fact(confirmed)`. Probe as before. Modes: `off`, `sep+add` (notes 01 + 04), `sep+add+rel` (this note).
Pre-registered: (1) rank of the wrong twin falls below the right fact in ≥ 90% of injected pairs under
`sep+add+rel` versus ≈ 50% (a coin flip on near-identical text) under `sep+add`; (2) no change on the uninjected
probes (recall@1 within 0.005); (3) `reliability` of uninjected facts stays at the prior unless verified.

**FactConsolidation-style test** (MemoryAgentBench's definition: later facts contradict earlier ones; multi-hop).
Generate chains `A → B → C` where C is corrected later by an outcome, and ask for the current value through one
hop. Score exact match. The SQL arm gets the same `rel_a`/`rel_b` columns and the same update rule; the hypothesis
is a **tie on single-hop**, and a Plexus advantage on **multi-hop** only if the SQL arm is not given a recursive
CTE for the `BASED_ON`/`DECIDED` walk. State the arm's code budget in the pre-registration, as L6 did.

Biggest risk: outcomes are rare in current data (the Acme recording has 4 decisions and 0 task failures caused by
a wrong fact). The mechanism is correct but idle until real runs produce failures; the benchmark has to inject them.

## 5. Confidence

- That PE-gated reliability demotes outcome-contradicted facts on the injected benchmark: **high** (the rule is
  designed to; the test checks the plumbing).
- That the latent-cause branches of `assert_fact` are an improvement: **medium**; they reduce "two live
  contradictions forever", which C3/C7 count as a feature, so this needs its own criterion (contradictions that
  outcomes later resolve should close; ones with no outcome should stay open).
- That it beats SQL: **low** on single-hop; the multi-hop path is a real but small engineering edge.
- That it matters on today's recordings: **low**; outcomes are too sparse.
